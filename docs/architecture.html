The merged pipeline: rules score, the LLM explains, HR decides

One pipeline, not two systems side by side. The graph, NLP layer, retrieval, HR loop, API and UI are ours. The ranking core takes Đán's ideas: every criterion scored by rule, the LLM out of the score, an arbiter judged in both orders, explanation cards, HR decisions that learn weights. Each ported part had to pass a rule written before measuring, on both benchmarks (, EVAL.md §8). Click any ID for its file and knobs.

Where the LLM is used

Requirements (T1), the clarification gate, the review that explains each shortlisted CV, near-tie arbitration (2 calls per pair), the report, and HR's plain-words re-weighting. Never for a score, a knock-out or the order outside near-ties.

What stays deterministic

Parsing, redaction, chunking, hedges, years, depth cue, retrieval, cross-encoder, knock-out, all 8 criteria, the fused order, the card, quality flags and the HR weight calibration. All unit-tested (101 tests), 0 tokens.

backend/app/agent/scoring.py · schemas.py

Scoring anatomy: who decides each number

Score(CV, JD) = 1[H(c)] × Σₖ w(c,k) · S(c,k) / 100

Since v3 all 8 criteria are rules over the parsed CV (), so the score is reproducible and every number quotes its CV line. The LLM's judgement of 5 of them is kept as a verified review that explains the candidate (). The weights come from per company type, or from HR at (sliders, words, or decisions that calibrate them).

Knock-out H(c)

Missing (or only hedged, ) a must-have and none of its accepted substitutes → total 0. Computed in , never by an LLM.

Ties and near-ties

Exact ties: orders by depth → years → relevance (0 tokens).
Near-ties (Δ < 0.05): asks the LLM in both orders (); the order changes only if both verdicts agree.

Evidence

The LLM review must quote the CV verbatim. checks every quote exists; also checks it supports the criterion. Ungrounded ones trigger ; after the budget the score is capped at 20 (not found) or 50 (listed, not demonstrated).

NLP pipeline: from a raw file to one CVProfile

Real CVs arrive as PDF / DOCX with broken diacritics, contact details and protected attributes, and no structure. Every CV (corpus or upload) goes through the same eight stages once; everything downstream reads the profile, never the raw file. Code order is X1 → X2 → X4 → X3 → X5 → X6 → X7: redaction runs before language detection, so no personal data ever reaches an index, a prompt or the UI ().

Chunking: three strategies, one is chosen by measurement

whole one vector per CV: long CVs truncate at 512 tokens and one vector blurs unrelated roles. Baselines B0–B2 use it.

window 120 words with 30 overlap: the textbook default, blind to CV structure.

structural one chunk per role / project / section with a contextual header, so a bullet is embedded with the role and dates it belongs to. The agent searches these.

The three are compared in . Mentions, years and depth cue are always read from structural chunks, whatever strategy is indexed.

One run, start to finish

Runtime sequence: stream, pause for HR, resume

A run is a LangGraph thread (thread_id = run_id). Each HTTP call streams until the graph ends or hits interrupt(); the checkpoint lets the next call continue exactly where it stopped.

1 → POST JD + profile + optional models. API validates model specs (), creates run_id, emits run_started with the Langfuse session URL.
2Builds run config: thread_id, callbacks [ Langfuse, usage], session metadata.
3 ⇄ astream(updates + custom). Nodes emit node_start / log / node_end (); state diffs become update events. Log lines are also appended to .
4, or interrupt(payload) → state checkpointed to → stream emits interrupt and ends. Usage is saved.
5 / → HR answers → Command(resume=body). The interrupted node re-runs from the top () and receives the answer.
6 → ENDOn approve, the stream emits done with the report and the run's total usage (all streams of this run).
7 → Any time later: GET /runs/{id} = checkpoint values + pending interrupt + usage + logs → ?run=<id> restores the full UI.

Events: run_started · node_start · log(info|loop|warn) · update · node_end · interrupt(clarification|substitutes|review) · done · error. Contract: docs/API.md.

Merge decisions: what was ported, what was measured, what was kept

Two benchmarks (): ours, 50 handwritten CVs × 12 JDs with silver labels (our dev set), and coding, Đán's 200 template CVs × 6 JDs (never used to tune our code; its gold follows rules like his scorer). Rule, written before running: a component becomes the default only if its nDCG@10 is not lower than the v2 baseline (B3 rules ⊕ CE) by more than 0.01 on either benchmark, and higher on at least one.

Before the merge: cross-evaluation

Each ranker won on its own data: on ours, ours 0.871 vs his 0.810; on his, his 0.858 vs ours 0.821. A home advantage on both sides is why the rule needs both benchmarks.

What we gave back

The ranking core he lacked: section-aware extraction, NegEx hedges and used / listed strength (traps@10 = 0), years from parsed dates, requirement-wise retrieval with the cross-encoder fused rather than used as a filter.

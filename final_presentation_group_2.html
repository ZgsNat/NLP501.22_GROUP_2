The problem

Keywords can't see what matters in a tester's CV

  • Depth: runs scripts (L1) → writes them (L2) → builds a framework (L3) → designs test architecture (L4).
  • Used vs listed: a tool in Skills is a claim; a project that used it is evidence.
  • Hedges: "familiar with Selenium", "currently learning Cypress".
  • Keyword ATS rewards stuffing; an LLM judge is opaque, position-biased and can invent evidence.

Our score

Score(CV, JD) = 1[H(c)] × Σk w(c,k) · S(c,k)
H = knock-out on must-haves · w = company-type weights over 8 criteria · S = 0–100 per criterion

Point 3 · Control

Every LLM output has a criterion, a check in code, and an action on failure

  1. The LLM never sets the score. Rules over the parsed CV do.
  2. Typed in, canonical out. Schemas; closed choice sets.
  3. Every claim is checked against the CV by code: quotes exist and prove the right thing; no tool or years the CV doesn't show; no protected attributes.
  4. Every failure has a defined action: retry with the exact failure, then drop or label.
  5. Humans own the decision: clarification, substitutes, approval, audit log.
  6. The controls are measured too, and no LLM judge is trusted before agreeing with humans.

Point 3 · The surprise

A stronger model needed more control, not less

nDCG@10 (ours / coding)JD read by qwen3:8bby Claude Sonnet
LLM-only JD parser0.884 / 0.8240.842 / 0.795
Hybrid parser (rules first, LLM fills gaps)0.876 / 0.7910.881 / 0.792
  • Sonnet reads JDs more strictly: "Jenkins or GitLab CI" became two hard must-haves (JD-008: 5 must-haves vs qwen's 2).
  • Knock-out misses rose from 9 to 17.
  • The deterministic JD parser keeps the reading literal; the hybrid is stable under both models.
Lesson: a better model is not a better system by default. Its extra capability showed up as extra confidence in a stricter reading, and only a control layer made the system robust to it.

Hybrid became the default by the decision rule we wrote before running: not worse by > 0.01 on either benchmark, better on one.

  • The arbiter catches position bias in 10% of verdicts.

Errors and limits

Where it fails, and what we can't claim yet

30 misses, 1 false alarm (12 JDs)

  • 13 on the vague JD: no concrete must-have, so only asking HR can fix it
  • 9 strict knock-outs: a good CV missing one stated must-have; L2 lets HR accept substitutes
  • the rest: weighting, mostly domain (a non-bank CV for a bank)
  • the one false alarm: a must-have only listed, never used

Limitations

  • open Silver labels from two LLMs: two teammates are grading 120 blind pairs; κ ≥ 0.8 keeps them
  • open Synthetic ranking data: consented real tester CVs being collected
  • 12 + 6 JDs: differences < 0.02 are not significant
  • Claude served through the Claude Code CLI as a stand-in for the API: behaviour carries over, latency and cost do not

Takeaways

What we would tell the next team building an agentic ranker

1 · Agentic where it earns it

Let the model decide what rules cannot: when to ask, how to read noisy text, which near-tie flips. Measure it by the paths it takes and the errors it prevents, not only by nDCG.

2 · Data work is measurable work

Measuring against external gold found 7 bugs, including a 100% name leak, that 100+ unit tests missed. Mask by deleting; structure CVs into facts.

3 · Control scales with capability

Write the criteria, check them in code, give every failure an action. The stronger model needed the control layer most.

## Summary
Senior QA automation engineer with seven years of experience, three of them with Playwright and TypeScript in a fast-releasing product company. I own end-to-end suites, build the test tooling around them and help developers write better tests. Before Playwright I worked with Selenium and with Cypress, which helps me judge which tool fits which problem.

## Work Experience

### Senior QA Automation Engineer, Online learning platform (2022 – present)

Joined when the team had a Selenium suite that took 70 minutes and failed unpredictably. Over six months I replaced it with a Playwright and TypeScript suite of about 420 tests. The suite uses a worker-scoped fixture to create a signed-in user through the API before each test, so tests do not depend on each other and can run in any order. Page objects are written as small typed classes with locators that rely on roles and test IDs, rather than CSS paths. Tests run in GitHub Actions in six shards, and the full regression finishes in 9 to 11 minutes on every pull request. Failure artefacts (trace, video, console logs) are attached to the run, which helped reduce the average time to diagnose a failed test from about 30 minutes to under 10.

I introduced API-level setup and checks through Playwright's request fixture, so UI tests focus on the behaviour that only a browser can verify. I also added component-level checks for the video player controls and an accessibility scan with axe on key pages. I work with the front-end team on selectors and on a seeded test environment that is rebuilt nightly. Flaky rate is monitored per test, and any test that fails twice in a week is quarantined and fixed within the sprint.

I coach developers: I wrote the team's test-writing guide, review test pull requests and pair with new joiners during their first feature.

### QA Automation Engineer, E-commerce agency (2019 – 2022)

Wrote and maintained Cypress tests in TypeScript for several client shops. Created a reusable set of custom commands and a template project, set up pipelines in GitLab CI and ran visual comparison checks for the main templates. Tested APIs with Postman and Newman. In 2021 I began evaluating Playwright for a client with Safari and Firefox requirements and delivered the first Playwright suite for that client.

### Test Engineer, Software outsourcing company (2017 – 2019)

Selenium WebDriver tests in Java for a web banking project, using Page Object Model and TestNG. Ran regression from Jenkins and updated the scripts when the UI changed. Wrote 120 new tests in my second year.

### Additional contributions

Beyond the day-to-day suite, I have taken on a few responsibilities that I find useful in a small product company. I am the owner of the release smoke test: a set of 25 tests that run against production after every deployment with a read-only test account and alert the team channel within three minutes if anything critical breaks. I also lead the monthly test-health review where we look at the slowest tests, the most frequently quarantined tests and the areas of the product with no coverage. This review has led to deleting around 60 low-value tests and adding 40 tests for payment and enrolment flows that were previously covered only manually.

I contribute to hiring: I designed a take-home exercise (build three Playwright tests for a small demo shop, with a short written note on what is not worth testing at UI level) and review submissions with the engineering manager. Candidates who explain their trade-offs usually do better than candidates who write the most tests.

I like to keep the tooling simple. The test repository uses a strict TypeScript configuration, ESLint rules that forbid fixed sleeps and unawaited promises, a pre-commit hook that runs the changed tests, and a short README that explains how to run tests locally against a seeded environment or against the pull request preview. New joiners usually run their first test within an hour of cloning the repository.

### Previous learning and side work

I follow the Playwright release notes and try new features (sharding, test annotations, trace viewer improvements) on a small sandbox repository before suggesting them to the team. I have given two internal talks on migrating a legacy Selenium suite without freezing feature work and on keeping UI tests independent of each other through API-level setup.

### Work style

I write short design notes for any change to the test architecture, ask a second engineer to review them, and keep a changelog in the repository so that the whole team knows when fixtures or helpers change. I prefer a few well-owned tests per user journey over a long tail of near-duplicates, and I delete tests that no longer protect anything. When developers ask for a test on a bug, I add the test in the same pull request as the fix if possible, so the regression suite grows from real defects. I treat the CI logs as a product: error messages from helpers explain what was expected, what happened and where to look next, which makes failures understandable for people who did not write the test.

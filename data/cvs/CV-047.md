## About me
Quality engineer with nine years in logistics and trade-finance software. I build the test machinery that lets a team ship safely: the harness that drives real browsers, the checks that call services directly, and the build jobs that run both after every change. I write most of it in Java.

## Work history

### Quality Engineer, Trade-finance software company (2019 – 2025)
Our product is a web application for letters of credit and guarantees, built by five squads. When I joined, regression testing meant three people clicking through a spreadsheet for four days before each release.

I designed and built the browser test harness from scratch on top of the standard WebDriver protocol. It has a base class that owns the browser session and its lifecycle, a small library of screen classes (one per page, with intent-revealing methods rather than raw locators), data builders that create customers and documents through the back end before a test starts, and a reporting layer that produces one readable page per run with screenshots at every failure. Five squads now add tests to it, and I review their changes.

To make it fast I packaged the browsers in containers and put a pool of 10 of them behind a hub. The nightly run of 1,400 browser scenarios went from just over six hours to about 45 minutes. Each scenario is independent and owns its data, so the scheduler can run them in any order and in parallel.

Alongside that, I wrote about 500 service-level checks that call the HTTP endpoints directly, using a fluent client library and the team's standard JVM unit test runner. They cover login, document submission, approval workflow, fee calculation and report export, and they run in under three minutes. When a user interface test fails, the matching service check usually tells us in seconds whether the problem is in the back end or the screen.

The build server runs the service checks on every merge request and blocks the merge when they fail; the browser harness runs on every release branch and nightly on the main branch. Over two years I brought the share of failures caused by the tests themselves from about one in eight to fewer than one in forty, by removing sleeps, isolating data, and writing a short rulebook that new tests must follow.

I also created a one-day course for new colleagues and a template for pull requests that asks "what could this test miss?".

### Test Analyst, Logistics software company (2016 – 2019)
Started as a manual tester for a warehouse management product. Within a year I was writing scripts for the most repetitive flows: goods receipt, picking and dispatch. By the end of this role I had about 150 automated browser scenarios and had set up a nightly build that mailed the results to the team.

### Junior Tester, Software company (2015 – 2016)
Manual testing, writing test cases and reporting defects.

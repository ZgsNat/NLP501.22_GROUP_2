Summary:
Performance test engineer with seven years of experience, the last four at an e-commerce marketplace where traffic can triple during campaigns. I design realistic workload models from production data, write load tests as code, run them in the delivery pipeline and explain the results to backend teams in terms they can act on. I prefer percentiles and saturation curves to averages, and I try to leave every team with a baseline and a threshold they own.

Experience:

Senior Performance Test Engineer — E-commerce marketplace
Jan 2022 – Present
● Built the performance testing practice from a single person to a small team: workload models, test data, environments, reporting and CI integration.
● Wrote k6 scripts in JavaScript for the main customer journeys (search, product page, cart, checkout) and for 25 backend APIs. Scenarios use arrival-rate executors and parameterised data, with thresholds on p95 and p99 latency and error rate.

● Created a Docker-based load generator setup and distributed k6 runs on Kubernetes jobs for tests above 8,000 virtual users.
● Wrote soak tests (6 hours) which exposed a memory leak in a recommendation service; helped the team reproduce and fix it.
● Report findings in two-page documents with graphs, a root-cause hypothesis and a recommendation; present results in the monthly reliability review.

Additional responsibilities and practices:
● Capacity planning: translate forecast order volume into requests per second per service and maintain a model of how many instances each service needs at peak, validated by load tests at 1x, 2x and 3x scale.
● Test data: created generators for realistic catalogues (2 million products), customer histories and carts, loaded into a pre-production database that mirrors production shape and cardinality, so that query plans and cache behaviour are representative.
● Environments: pre-production runs on the same instance types as production at about half the size; results are extrapolated only for components where scaling is linear, and the remaining services are tested at full size once per quarter.
● Dependencies: wrote stubs for payment gateway, shipping and email partners with configurable latency and error rates, so tests do not hit partner sandboxes and can simulate partner degradation.
● Observability: added trace and correlation identifiers to test traffic so that backend teams can filter test requests in logs and traces; alerts are muted for known test traffic labels.
● Communication: send a short weekly performance note (what regressed, what improved, what is risky); coach backend developers to write their own k6 smoke tests for new endpoints.
● Mentoring: onboarded two junior performance engineers in 2023 and 2024, and gave an internal training on reading percentile latency graphs and on common bottleneck patterns (thread pools, connection pools, N+1 queries, garbage collection pauses, lock contention, cache stampedes).
● Tooling choices: k6 for pipeline-embedded tests and developer-owned scripts because scenarios are plain JavaScript and thresholds are first-class; JMeter where a team already owns plans or needs protocol coverage (JDBC, JMS) that k6 does not provide natively.
● Reporting: each run publishes a link to its Grafana dashboard with start and end timestamps, so that anyone can inspect the system during the exact test window.
